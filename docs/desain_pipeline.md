```
        out/transaksi_bersih.csv ─> P5_fact_penjualan ─────────┴──> fact_penjualan
```

Dimensi produk dan pelanggan tidak bergantung pada keluaran P1, sedangkan dimensi
waktu dan tabel fakta membaca berkas `out/transaksi_bersih.csv` yang dihasilkan P1.
Karena itu workflow menjalankan P1 lebih dahulu, dan pengosongan tabel data
warehouse dilakukan setelah P1 selesai agar kegagalan cleansing tidak mengosongkan
isi data warehouse.

## Aturan cleansing P1

| Tahap | Aturan |
| --- | --- |
| Buang Duplikat | Kunci `id_transaksi`, membandingkan nilai baris pertama yang diterima |
| Normalisasi | Empat pola tanggal, harga dengan awalan Rp dan pemisah ribuan, qty bilangan bulat |
| Cek Validitas | Baris ditolak bila id transaksi kosong, tanggal tidak ada di kalender, qty bukan bilangan bulat, qty negatif, qty nol, harga bukan bilangan bulat positif, id produk kosong, id pelanggan kosong, atau metode bayar kosong |
| Pilih Bersih | Menghitung `total_penjualan = qty x harga_satuan` |
| Pilih Ditolak | Menyimpan nilai mentah sumber dan kolom `alasan` |

## Normalisasi dimensi produk

Kategori dinormalisasi dengan urutan: rapikan spasi, ubah ke huruf kapital di awal
setiap kata, ganti penyambung `Dan` menjadi `&`, lalu isi `Tidak Diketahui` bila
kategori kosong. Hasil akhir pada master produk:

| Kategori mentah | Kategori tersimpan |
| --- | --- |
| Elektronik, elektronik | Elektronik |
| Fashion, FASHION | Fashion |
| KESEHATAN & KECANTIKAN, Kesehatan & Kecantikan, Kesehatan dan Kecantikan | Kesehatan & Kecantikan |
| Makanan & Minuman | Makanan & Minuman |
| Mamin | Mamin |
| Olahraga, olahraga | Olahraga |
| Rumah Tangga, rumah tangga | Rumah Tangga |
| kosong | Tidak Diketahui |

Kategori `Mamin` sengaja tidak digabung dengan `Makanan & Minuman` karena keduanya
memakai merek dan jenis barang yang berbeda.

## Normalisasi dimensi pelanggan

Kota yang kosong atau NULL diisi `Tidak Diketahui`. Nomor telepon dibersihkan dari
seluruh karakter non angka, lalu awalan `62` diubah menjadi `0` dan nomor yang
tidak diawali `0` diberi awalan `0`.

## Surrogate key dan lookup

Setiap tabel dimensi memakai kolom `GENERATED BY DEFAULT AS IDENTITY`. Pipeline P5
mengambil key tersebut dengan transform Database Lookup pada kunci alami dimensi:
`tanggal` untuk dimensi waktu, `id_pelanggan` untuk dimensi pelanggan, dan
`id_produk` untuk dimensi produk.

Produk yang tidak ditemukan di master menghasilkan `product_sk` bernilai 0. Baris
tersebut dipisahkan oleh Filter Rows dan ditulis ke
`out\transaksi_produk_tidak_dikenal.csv` sehingga tidak pernah masuk tabel fakta
dan kunci asing tabel fakta tetap utuh.

## Kosongkan tabel

Action SQL milik Hop menjalankan satu pernyataan berikut sebelum muat ulang:

```
TRUNCATE TABLE fact_penjualan, dim_waktu, dim_produk, dim_pelanggan RESTART IDENTITY
```

Keempat tabel ditulis dalam satu pernyataan karena PostgreSQL menolak
pengosongan tabel induk yang masih dirujuk foreign key. Pernyataan `TRUNCATE`
untuk tabel induk dan tabel anak harus issued bersamaan, sedangkan truncate satu
per satu akan gagal dengan pesan `cannot truncate a table referenced in a foreign
key constraint`.

`RESTART IDENTITY` dipakai agar surrogate key juga kembali ke awal, sehingga dua
menjalankan berturut-turut menghasilkan isi tabel yang identik, bukan hanya jumlah
baris dan total yang sama.

## Penanganan tanggal

Kolom `tanggal` pada `dim_waktu` dan `fact_penjualan` bertipe `DATE` di PostgreSQL.
Pada pipeline P4 dan P5, kolom tanggal dibaca oleh CSV Input sebagai tipe Date
dengan format `yyyy-MM-dd`, sehingga nilainya sudah berupa objek tanggal ketika
mencapai Database Lookup dan Table Output.

Transform SuperScript pada P4 membaca komponen tanggal dengan memeriksa apakah
nilai tersebut menyediakan `getFullYear` atau `getYear`, sehingga tetap bekerja
apabila nilai tanggal diekspos sebagai objek Date Java atau sebagai objek Date
JavaScript. Atribut kalender yang dihasilkan adalah hari, nama hari, bulan, nama
bulan, kuartal, dan tahun.
